# Стандарты и стиль технической документации (Style Guide)

Данное руководство определяет единые стандарты составления и оформления технической документации в проекте в соответствии с лучшими практиками.

---

## 1. Стиль изложения

- **Императивный стиль инструкций**: В пошаговых руководствах (How-To, Tutorials) используйте повелительное наклонение глаголов («Выполните», «Создайте», «Запустите», «Установите»).
- **Лаконичность и точность**: Избегайте неопределенностей, вводных слов и пассивного залога, где это возможно.
- **Единообразие терминов**: Используйте термины строго в соответствии с глоссарием.

---

## 2. Оформление Admonitions (Callout-блоков)

Для привлечения внимания к важной информации используйте стандартный синтаксис предупреждений GitHub / MkDocs Material:

```markdown
> [!NOTE]
> Важная информация или контекст, на который следует обратить внимание.
```

```markdown
> [!WARNING]
> Предупреждение о возможных рисках, сбоях или критических ограничениях.
```

Пример отображения:

> [!NOTE]
> Конфигурационные файлы должны храниться в формате YAML или JSON.

> [!WARNING]
> Не сохраняйте секреты и приватные ключи в публичных репозиториях.

---

## 3. Глоссарий терминов

| Термин | Описание |
| :--- | :--- |
| **Docs-as-Code** | Подход к работе с документацией как с кодом (хранение в Git, автоматическая проверка в CI/CD, сборка статическими генераторами). |
| **mTLS** | Mutual TLS — двухсторонняя аутентификация по протоколу TLS с использованием сертификатов клиента и сервера. |
| **OpenAPI** | Спецификация для описания REST API в формате YAML или JSON. |
| **Spectral** | Линтер для проверки соответствия OpenAPI/AsyncAPI спецификаций установленным правилам. |
| **Diátaxis** | Фреймворк систематизации технической документации по 4 категориям (Tutorials, How-To, Reference, Explanation). |

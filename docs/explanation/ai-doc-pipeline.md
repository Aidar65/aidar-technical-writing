# Генерация и проверка документации с помощью локальных LLM

Статья объясняет, как устроен мой пайплайн документации. Локальная нейросеть готовит черновики и сверяет их со спецификациями. Финальное решение принимает технический писатель. Модели работают внутри изолированного контура предприятия, поэтому данные не покидают периметр.

**Контекст для читателя.** Статья выросла из внутренней документации. Её читали инженеры, которые уже знали Ollama и Aider. Для портфолио я расширил введение и добавил контекст. Техническую часть я сохранил без изменений. Так видны обе версии текста: для эксперта и для широкой аудитории.

---

## Архитектура пайплайна: Ollama и Qwen2.5-Coder

Пайплайн работает внутри изолированного периметра и не обращается к интернету.

```text
[ Исходники кода / OpenAPI ]
           │
           ▼
[ Ollama Server (Qwen2.5-Coder) ] ── (Контекст: ГОСТ 34/19 + Diátaxis)
           │
           ▼
[ Генерация Markdown / Спецификаций ]
           │
           ▼
[ Ревью и нормоконтроль: технический писатель ]
           │
           ▼
[ Quality Gate: markdownlint ] ── (Автопроверка в CI/CD)
```

---

## Компоненты архитектуры

1. **Ollama Inference Engine**: локальный сервер инференса. Сервер работает в закрытом контуре.
2. **Qwen2.5-Coder**: языковая модель для работы с исходным кодом. Модель генерирует OpenAPI-спецификации и форматирует Markdown.
3. **Ревью человеком**: технический писатель проверяет черновик и проводит нормоконтроль. Он же решает, публиковать ли текст.
4. **Compliance & Quality Gates**: CI проверяет тексты линтером `markdownlint` и валидаторами схем. Коммит в Git проходит только после успешной проверки.

---

## Преимущества решения в закрытых контурах

- **Безопасность air-gapped-контура**: данные не выходят за пределы периметра компании.
- **Стандартизация**: модель соблюдает правила форматирования ГОСТ и Diátaxis уже при генерации.
- **Скорость**: первичная подготовка технической документации занимает до 70% меньше времени.
